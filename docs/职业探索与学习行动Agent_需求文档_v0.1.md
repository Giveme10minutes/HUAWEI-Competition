## 1. 项目定位与依据

面向不同专业、不同年级、处于职业探索与成长阶段的计算机相关专业大学生，结合个人兴趣、能力证据、时间条件及可追溯的岗位信息，提供职业方向比较、阶段学习任务、成果反馈和动态调整。

核心流程：了解用户及所处阶段 → 明确当前问题与优先目标 → 查询职业与路径依据 → 安排可承受的行动实验与必要学习 → 收集结果与体验 → 调整方向和计划。

以学期阶段目标连接近期行动。用户暂未确定职业时，职业访谈、工作活动体验及补齐决策信息也可以成为有效目标，不必先确定目标岗位。

老师提出的需求包括：定时收集行业趋势和招聘信息、建立知识库、根据职业意向建议学习路径、跟踪学习过程并提出建议。本方案全部保留；自动采集按数据源逐步实现，第一版先保证经人工审核的数据可以导入、查询和更新。

资料依据：教育部既有职业规划指导方案强调个人情况、市场需求、学习实践及动态调整，可用作产品设计参考，不能当作华为 ICT 大赛评分规则。[教育部相关通知](https://tf.ncss.cn/ncss/jydt/yw/202410/20241023/2293345859.html)；O*NET 将兴趣探索作为职业探索的工具，支持我们把兴趣作为输入之一，而不是由一次问答决定职业。[O*NET Interest Profiler](https://www.onetcenter.org/IP.html)

补充核验：已于2026-10-31读取本届创新赛官网公开赛题、阶段材料和评分表，见[赛事规则核验](赛事规则核验_2026-10-31.md)。初赛创新性60%、应用价值40%；附件提交截止、能否重传、本校时间与实际资源额度仍未确认，不承诺已满足全部参赛要求。

## 2. 目标用户与待验证问题

### 2.1 目标用户（已由用户确认）

服务计算机相关专业大学生，涵盖不同专业、年级、兴趣及职业意向，包括尚无明确方向、希望了解本专业去向、考虑跨专业发展、已有目标并希望付诸行动的学生。不能默认用户已有编程基础、只准备开发实习或已有目标岗位。

产品采用统一探索流程，按职业领域接入不同资料和任务标准。专业作为背景与资格参考，不据此固定可选职业；允许发现专业内、跨专业和复合型路径。

需覆盖三类状态：

- 未定向型：不知道自己喜欢什么或适合什么，先通过经历回顾、工作偏好和体验活动逐步形成候选方向。
- 探索型：有兴趣但不清楚日常工作和能力要求，需要比较方向并做小任务体验。
- 目标型：已确定岗位方向，需要知道差距、安排任务并持续调整。

### 2.2 需求假设

H1：用户难以把兴趣、专业背景与职业世界联系起来；形成意向后，也难以将职业要求转成可执行的学习任务。

H2：通用学习路线无法适应用户的基础、时间和现有成果。

H3：用户完成课程或打卡后，不清楚是否能独立应用。

H4：用户在任务卡住或时间变化时，需要具体调整建议。

H5：相同年级的学生也可能有不同的学业条件、经济约束和实践机会，固定年级路线难以适用。

H6：用户可能持续看课或收藏资料，却缺少真实尝试；也可能把对某项活动的消费兴趣误认为对其工作过程的兴趣。

H7：部分学生首先需要比较就业、升学等路径及其代价，而非立即得到一张技能课程表。H5—H7 为从个人经验材料提炼的待验证假设。

上述问题来自本次讨论，尚未通过访谈证实。开发前建议访谈来自至少三类专业背景、不同年级和目标明确程度的 6—10 名同学，记录一次真实选方向或学习受阻的经历、现有解决方式及希望获得的帮助；不要只询问“会不会使用这个产品”。

### 2.3 项目目标

1. 让用户了解推荐方向的依据、限制和待验证点。
2. 将岗位能力差距转为可在现有时间内完成的任务。
3. 用任务成果和解释来评估进展，区分自述与已验证能力。
4. 根据实际反馈调整计划，并保留调整前后记录。

首版不以获得 offer、提高薪资或找到“唯一正确职业”作为验收指标。

## 3. 范围与优先级

P0 为首次可用版本必须实现；P1 为闭环完成后的增强功能；P2 为后续探索。

| 模块 | P0 首版 | P1 增强 | P2 探索 |
| --- | --- | --- | --- |
| 用户档案 | 跨专业的兴趣、经历、目标、能力、时间与约束档案 | 简历辅助提取并由用户确认 | 更多输入与交互方式 |
| 岗位资料 | 经审核的岗位导入、筛选、来源追溯 | 对许可数据源定时增量更新 | 多源大规模接入 |
| 行业信息 | 人工审核的资讯及来源查询 | 资讯定期更新、变化提示 | 长期趋势分析 |
| 职业探索 | 未定向探索、本专业与跨专业候选比较，每轮最多三个方向 | 扩充已核验职业资料与体验任务 | 经验证的测评工具集成 |
| 学习计划 | 阶段目标与近期行动关联、两周默认计划、前置条件和预算 | 多学期规划、关键日期提醒 | 长期学习路径优化 |
| 阶段与资源 | 当前学期、学业约束、用户录入的关键日期和可用资源 | 校内资源核验与机会推荐 | 自动接入校历与更多资源 |
| 发展路径 | 记录路径疑问，提供待核实问题和低成本探索任务 | 就业、升学等结构化方案比较 | 更多路径及专业支持 |
| 学习跟踪 | 文本、作品、实践记录等成果提交、反馈、评估、计划版本 | 经授权的作品集与学习平台接入 | 分领域的专用验收工具 |
| 成长记录 | 差距清单、成果和计划调整记录 | 导出报告 | 经授权的导师查看 |

首版面向计算机相关专业大学生提供通用探索与行动流程；对职业知识、任务与专业评估的覆盖深度单独标识，不宣称所有职业均有完整专家级支持。资料不足的领域继续支持经历梳理、职业调研和行动记录，并明确待补资料。

首版不做自动投递、付费课程购买、心理诊断、就业概率预测或在用户设备上自动执行代码。就业、升学和资格准备可作为用户路径条件参与比较，但首版不扩展成全学科备考辅导平台。

## 4. 关键用户流程

### 4.1 首次使用

1. 用户可直接用模糊表达开始，也可选择探索入口；协调 Agent 从具体经历或当前困惑切入，默认每轮一至两个必要问题，允许不知道、跳过和纠正。不要求先填写完整档案或自行完成深入分析，已有明确内容不重复询问。此为本版目标行为，尚未验证。
2. 系统提取档案，区分已知、未知和需要确认的信息；用户确认后保存。
3. 未定向用户先进行经历与工作活动探索，再查询职业介绍、行业信息和岗位样本；有目标的用户结合地区、发展阶段等查询资料。不同领域按需核对学历、资格与实践条件。
4. 展示方向卡片：实际工作、个人适配依据、能力差距、约束冲突、岗位证据及不确定性。
5. 用户选择阶段目标；还无法选择时，安排一至两个方向体验任务。
6. 结合本学期优先目标和已知关键日期，生成近期行动计划（默认两周）；用户确认后成为当前计划。

### 4.2 学习与复盘

用户查看任务 → 学习并实践 → 提交成果和困难 → 系统按验收标准给出反馈 → 用户补交或确认完成 → 更新能力证据 → 提出下一阶段计划 → 用户确认。

计划变更必须说明触发原因、修改内容和影响，不直接覆盖历史。

### 4.3 时间或目标变化

用户减少可用时间或更换目标时，系统读取当前进展，保留已完成成果，生成新的可行计划。建议切换职业方向时须展示依据，由用户决定；一次失败不能直接推断“不适合该职业”。

## 5. 详细功能需求

### FR-01 建立与维护个人档案（P0）

输入：年级、专业、预计毕业时间、兴趣活动及原因、已学知识与技能、课程/社团/项目/志愿服务/兼职等经历、职业意向、目标城市、每周学习时间、预计实习时间、每周到岗天数与实习时长。补充可选字段：当前学期、学制、课程/毕业必需任务、当前最想解决的问题、工作环境偏好、可支配实践预算区间、是否需要兼顾兼职、可接触的校内外资源及不能牺牲的条件。经济与家庭情况可不提供，优先询问可接受的成本和时间，不要求收入或资产明细。姓名、手机号、身份证、完整学校信息不作为使用前提。

要求：

- 支持不知道和暂不填写；缺失条件保留为未知，不自动补造。
- 每项能力记录证据等级：用户自述、已提交材料、已通过任务验收；材料提交不自动等于掌握。
- 首版使用开放式兴趣与工作偏好问题，不冒称标准化心理测评；例如“在组织活动、解释知识、分析问题、创作作品或动手实践中，哪些经历让你愿意持续投入？请举例”。
- 模型提取的信息必须让用户确认，用户可以修改或删除。

验收：用户每周学习时间由 8 小时改成 4 小时后，新计划按 4 小时生成；未提供毕业时间时，不声称其符合某届招聘资格。

### FR-02 导入岗位与行业资料（P0）

管理员可通过表单或结构化文件录入经审核资料；用户可粘贴目标岗位描述，并补充链接和获取日期。首版不承诺任意招聘链接自动解析成功。

职业资料必须记录职业领域、典型工作活动、发展路径、能力与资格要求、来源和更新时间，并关联岗位样本；不能把单个招聘广告等同于完整职业描述。

岗位必须记录：内部编号、岗位名称、企业、方向标签、地点、招聘类型、职责、必需技能、优先技能、学历/届别/到岗条件、来源链接或用户提供说明、原文片段、采集时间、原文发布日期（允许未知）、有效性状态。

行业资讯另存：标题、发布机构、发布日期、适用地区/行业、主要事实、来源及人工审核状态。新闻观点不能转换为确定的就业机会判断。

规则：

- 技能必须能回指原文；明确区分必需项、优先项和信息未提及。
- 同一岗位依据来源 ID 或企业、名称、地区与正文特征去重；修改后保留版本，不累计为新增岗位。
- 缺少来源、正文为空或字段冲突时进入待审核，不进入正式推荐依据。
- 用户自贴材料标为“用户提供，未独立复核”，不混入公共统计。

验收：同一岗位重复导入两次，正式统计仍为一条；原文仅说“优先”时，不提取成硬性要求。

### FR-03 查询、更新与时效管理（P0/P1）

P0 提供筛选查询、人工更新和最后核验时间；P1 才对已确认许可和可访问的数据源启用定时任务。

建议规则（待试运行调整）：每周检查岗位链接与状态；超过 30 天未成功复核的资料标为“需要复核”；招聘页明确关闭则标为失效并退出当前机会列表，但保留历史技能参考。发布日期未知不能表述为“最近发布”。

自动更新采用新增/变更/失效记录，经人工审核后进入推荐库。抓取失败保留上一份快照并提示陈旧；不能用模型生成的招聘信息填补失败。重复运行不得产生重复记录。

验收：更新源不可访问时显示最近成功时间和失败状态，不能显示“已更新”；失效岗位不作为当前在招机会。

### FR-04 职业方向比较与建议（P0）

结合兴趣、工作偏好、能力证据、时间约束和岗位样本，最多给出三个方向。顺序为：了解经历与工作偏好 → 形成候选职业 → 查询职业及岗位依据 → 比较能力与资格差距 → 指出未知条件 → 提供探索行动。用户尚未有方向时不得跳过探索、直接要求选择职位。

每个方向必须包含：行业与岗位职能的分别说明、日常工作活动、支持推荐的个人信息、主要差距、进入条件、工作环境与代价、至少一条真实来源（无来源时明确不足）、下一步验证任务。同一行业可有不同职能，同一职能可跨行业，不按专业或热门行业名称直接判断适合。

区分“喜欢某个领域的内容/产品”和“愿意承担该职业的日常任务”，必要时提供小型体验。薪资只是用户可选的权衡维度，需兼顾稳定性、地区、工作方式、成长空间与个人条件；不得因行业标签推断高薪或个人回报。

不显示没有校准依据的“适配度 92%”“成功率 80%”。明确不满足的硬条件必须展示；条件未知不能当作满足。推荐的学习方向与用户当前可投递的具体岗位应分开展示。

样本不足时可提供探索建议，但不得给出行业热度排名。若计算技能出现频率，须写明筛选范围、时间、分子和分母，只表示该样本内频率。

验收：仅有两个岗位样本时，结果明确说明范围有限；岗位要求硕士而用户为本科时，显示条件冲突，不能因技能相似而隐藏。

### FR-05 建立技能差距清单（P0）

为目标方向建立技能项、前置关系、岗位依据、个人证据与下一步验证方式。状态为“未知、待学习、学习中、已提交证据、已通过本项目任务验收”；最后一种只证明特定任务表现，不证明能胜任整个岗位。

优先级综合必需程度、前置关系、当前目标和可用时间，不单纯按关键词频率排序。模型建议的技能关系需经管理员审核后纳入公共技能库。

验收：用户说“擅长沟通”，系统先记录为自述，并可通过访谈提纲、情境表达等任务收集证据；编程、设计、运营等方向分别使用适合本领域的任务，不统一用代码评估。

### FR-06 生成两周学习计划（P0）

每个任务包含：关联阶段目标、任务类型（探索/学习/实践/复盘）、待验证的问题或目标能力、前置条件、具体动作、参考资料、预估时间与可选成本、提交成果、验收标准、遇到困难时的求助方式。

探索计划应含至少一个能接触真实工作活动或外部反馈的可执行任务，并允许用户选择无费用、可模拟或校内替代方案。学习任务说明将用于解决什么问题；不机械要求所有知识都边做边学，需先满足专业基础与安全前提。

用户连续收藏或学习、没有实践时，先询问阻碍与偏好，再提出缩小后的第一步，不贴“懒惰”“逃避”等标签。

建议总任务时间不超过用户两周可用时间的 80%，剩余用于复习、实践受阻处理和复盘。时间估计是可修改的计划值；必要基础无法在周期内补齐时，只规划当前阶段并解释后续差距，不承诺短期掌握所有岗位要求。

行动可以是课程学习、职业访谈、资料分析、创作、调研、社团或志愿实践、模拟工作等；每项说明它帮助验证什么兴趣或补足什么能力。计划周期可调，两周仅是首版默认行动周期。

资源优先专业机构、高校、官方教程和免费可访问内容；保留资料标题、链接、适用版本和最近核验时间。官方教程可能仍有前置门槛，不能仅因“官方”就视作适合零基础。

验收：每周 4 小时用户的两周计划任务估计合计不超过 6.4 小时；没有前置基础时先安排基础或诊断任务。

### FR-07 成果提交与任务反馈（P0）

支持文本、文档/作品链接、调研与访谈记录、实践反思等通用成果，代码和运行结果仅是技术方向的可选形式。按职业领域配置评估标准，例如调研看方法与证据，设计看目标与决策说明，组织实践看过程与复盘。

P0 不自动执行上传代码，不将未经验证的专业判断表述为专家结论。无法读取作品内容时要求用户提供摘要或可读材料；用户自报经历标明来源。

输出状态：未开始、进行中、待补证据、需修改、已通过任务验收。每次反馈列出满足项、缺失项、具体补交动作和评估限制。证据相互矛盾时追问，不能默认通过。

对于探索任务，行动已执行但结果不理想、发现不喜欢或排除一个方向，也可以是有效证据；记录实际行动、外部反馈、喜欢/不喜欢的工作环节及下一步。不能只按销量、录用或流量判断成长，外部结果不完全由个人能力决定。

除产出要求外，可安排一至两个理解问题；回答不充分时给提示并允许重试。页面不得将“点击完成”“上传文件”和“掌握技能”合并。

验收：只有“我做完了”的反馈进入待补证据；关键功能缺失时指出对应验收项，而不是泛泛表扬。

### FR-08 学习过程答疑（P0，限当前任务）

针对当前任务提供分级提示、概念解释、方法指导、资源建议和困难分析；用户可选择提示模式或直接讲解。回答尽量引用当前任务资料；没有查到依据时说明是一般建议。先区分知识不足、目标模糊、资料不足、时间冲突和执行困难等情况，不未经许可修改用户成果。

验收：用户说“职业访谈不知道怎么开始”，系统围绕访谈目的帮助拟定问题与执行步骤；技术任务才采用代码与日志排查。

### FR-09 复盘与计划调整（P0）

触发：用户主动复盘、阶段结束、任务困难反馈、可用时间或目标变化。P0 采用站内提示和用户触发；后台通知为 P1，不能假设关闭页面后模型仍在持续工作。

调整规则：

- 时间不足：减少任务或延长周期，优先保留必要前置任务。
- 基础薄弱：插入补充练习，调整后重新检查时间预算。
- 任务已会：依据验收成果跳过或提升难度。
- 兴趣变化：给出新的探索任务和备选方向，由用户确认切换。
- 岗位资料变化：解释变化范围，不因单条岗位更新立即推翻路线。

保存触发原因、依据、新旧任务差异和确认时间。生成新计划时保留旧版及已完成成果。

验收：用户拒绝建议后当前计划不变；修改时间预算后新计划满足预算且历史仍可查看。

### FR-10 成长看板与记录（P0）

展示当前目标、下一项任务、任务完成情况、技能证据、岗位来源更新时间和计划调整记录。进度以“通过任务数/计划任务数”表达，不称为“就业能力百分比”。

每次经历保留背景、目标、个人职责、具体行动、结果、证据及复盘。自述成果与可核验成果区分，团队成绩不能自动算作个人贡献；复盘记录可供后续整理作品集或经历说明。

用户能查看、更正、导出文本记录和删除个人档案。用户明确删除后，其记录不能再被后续推荐检索使用。

### FR-11 内容与运行管理（P0）

管理员能审核岗位与学习资源、维护技能名称与别名、查看采集失败、维护验收标准。记录工作流版本、资料版本、调用结果、耗时和错误，便于复现建议的生成依据。

失败状态必须可见；模型或平台调用失败时保留已保存的数据并允许重试，不生成看似成功的占位结果。

### FR-12 阶段目标与关键事项协调（P0）

根据学制、学期、当前状态和用户确认的信息，形成少量阶段优先目标；年级只是提示，不强制“大二必须定方向”或“大三必须完成某段实习”。新入学适应、毕业必需任务与用户自定目标应纳入时间协调。

维护关键事项的日期、来源、适用对象、核验状态及其关联任务。P0 由用户录入或人工审核，不自动假定通用招聘月份、保研条件或本校规定；未知时提供核实事项。已确认的考试、课程和毕业任务占用时间后，再分配探索行动。

验收：同为大一，已适应的学生与需要先处理课程问题的学生得到不同近期建议；遇到考试周时降低额外任务负担，不能忽略已确认的硬性截止日期。

### FR-13 发展路径比较（P1，P0 先收集疑问）

用户纠结就业、研究生学习、其他深造或资格路径时，比较目标动机、进入条件、实际活动、时间与成本、可能收益、机会成本、尚待核实的信息及可保留的备选路线。用户对研究的兴趣可通过文献阅读、访谈、受指导的小课题等尝试探索，不由“喜欢学科”直接推断。

不以固定学历比例、学校层次、单条招聘要求或同伴选择自动决定是否考研。资格、报名、培养及费用等事实须查适用机构的有效资料。用户选择一条近期主线并按需保留可承受的备选，避免同时分配多套超出预算的完整计划。

输出是方案比较及下一步取证任务，重大取舍由用户确认；不自动报考、投递或承诺升学与就业结果，也不扩展为各科备考教学。

验收：用户只说“室友都考研”时先补问目标与条件，提出取证行动；未知成本和规则保留未知，不给强制结论。

### FR-14 利用现有资源与比较实践机会（P1）

记录用户愿意使用的课程项目、社团、老师、校友、公开数据、本地机构等资源；按目标和预算建议可行的行动入口，缺少实习机会时可提供校内项目、职业访谈或模拟任务替代。

比较社团、项目或实践机会时，关注实际工作、学习空间、个人职责、可形成证据、时间/费用和学业冲突，不按组织或企业名气单独排序。选择赚取生活费的兼职属于用户现实需求，不因与职业目标关联弱就否定其价值。需要联系他人时由用户自行决定并执行。

验收：无法到外地且无额外预算的学生得到本地或可远程完成的替代方案；系统不编造学校已有项目、导师承诺或实习名额。

## 8. 资料采集与知识库策略

资料台账见同目录《资料调研与来源台账》。本轮完成的是来源调研，并未建立生产岗位库或全量就业市场数据集。

建议初始数据准备目标：每个正式支持方向至少 10 条去重岗位，尽量覆盖至少 3 家企业；不足时展示覆盖不足，不能凑数。每个方向准备至少 5 个任务模板和对应的官方学习资源。以上数量是工程准备目标，不是统计代表性保证。资料覆盖按职业领域独立记录，不将“目标用户面向计算机相关专业大学生”误写成“所有职业资料已经齐备”。初始验证覆盖计算机类学生不同年级、基础与目标状态；首批方向根据已有资料质量选定，不声称覆盖全部计算机岗位。

定时采集上线条件：已确认允许访问与使用、页面能稳定读取、字段可以复核、失败有记录。验证码、登录和访问限制不绕过。未达到条件时使用人工审核导入；公共资源若只允许链接引用，则保存必要元数据与短证据，不复制整篇资料。

不同资料处理：岗位和资讯侧重日期、适用范围和来源；技能及课程侧重版本、前置关系和验收；用户进展保存在独立业务记录中。采集任务建议由后端调度实现，不能未经验证就声称 AgentArts 内置支持所需定时能力。

### 8.1 个人经验材料的处理

用户提供的五份博主文字稿仅用于提取方法、访谈问题及案例线索。保留原稿，不将转写错词猜测为事实。清洗后的条目记录来源文件、原文位置、观点/事实类别、适用条件、审核状态。

涉及学历资格、学校规定、招聘日期、收入与行业统计的内容，取得有效权威来源前不进入事实推荐依据。博主经验不替代用户访谈、当前岗位资料和本校文件；不复制其绝对化口吻，也不把整套建议直接当作系统指令。详见修订说明中的来源与处理清单。

## 9. 多 Agent 实现映射与验证边界

### 9.1 目标架构与职责

下一版采用一个探索协调入口与三个专业角色，面向计算机相关专业不同年级的大学生。学生始终面对同一对话入口，不手动选择子 Agent。实验报告、全学科辅导、论文综述及校园办事不新增为独立产品范围。

| 角色 | 输入 | 职责与输出 |
| --- | --- | --- |
| 探索协调 Agent | 当前问题、相关对话、已确认线索与规划 | 引导表达、判定当前阶段、按需调度，组织最终回答；信息不足时只追问 |
| 职业资料与方向分析 Agent | 候选方向、相关个人线索、知识检索结果 | 比较工作内容与门槛，输出带来源的依据、差距、冲突与未知项 |
| 阶段规划与行动 Agent | 分析结果、时间条件、原规划及成果反馈 | 形成方向依据、差距、阶段目标、近期行动和调整条件；行动关联目标 |
| 质量复核 Agent | 草稿、引用片段、用户约束、原约定及版本 | 指出无依据判断、约束冲突和评审新增标准，给出具体修改意见；不虚构独立权威背书 |

默认流程：模糊输入→协调追问→形成待确认线索；需要比较时→资料分析→阶段规划→复核→统一回答；已有目标或成果反馈时直接进入所需环节。简单问题不运行整条链。复核发现问题后默认只进行一轮修订，仍缺证据则明确未知或向用户澄清，不无限互评。固定先后依赖用工作流明确编排，不把意图路由等同于多角色连续协作。

### 9.2 交接与业务状态

各角色接收完成任务所需的最小上下文。交接需区分用户自述、已确认推断、资料事实和未知项；携带来源标识、资料日期、相关片段及当前规划版本。下一角色不得把上游推断升级为事实；资料不足时返回缺口，不编造证据。角色失败需标识未完成环节，不将半成品标为已复核规划。

Agent 只提出草稿。网页确认后由后端校验并保存；待确认内容不得冒充当前正式记录。预算换算、分项求和、版本和去重由程序负责，复核 Agent 不能替代确定性校验。用户改预算、纠正经历或拒绝草稿时，以最新确认记录为准；旧规划和原成果保留，评审沿用原约定。

### 9.3 知识库、Skill 与 MCP

知识资料按职业与路径、亲历与探索案例、学习实践资源、规划方法案例四类组织，先分类复用，是否分库根据检索效果决定。职业体验优先知乎等交流平台的亲历和访谈，保留作者背景、日期、链接、适用范围及亲历/观点/事实类型；岗位门槛对照招聘原文，资格规则核对对应机构原文。上传或采集不等于审核通过；不能把个人经历变成行业统计。

项目内职业规划 Skill 保留为方法维护材料，提取相关步骤写入各角色提示词；首轮验证不依赖运行时加载 Skill。必须执行的确认、引用和评审规则放入提示词及业务代码，不仅放在知识库等待召回。暂不新增 MCP 服务；检索优先使用平台知识库，保存沿用后端 API。以后确需实时外部查询再评估普通 API、插件或 MCP。多 Agent 不自动获得联网、定时更新或数据库写入能力。

### 9.4 已有基础与待验证能力

已有本地 React/TypeScript/shadcn 界面、FastAPI/SQLite、低码单智能体发布调用、流式回答和已确认记录传入。仍为单用户本地原型；自动草稿整理、完整成果闭环、多用户隔离和公网部署未完成。多 Agent 尚未配置或联调，不能将现有单 Agent 成功视为新架构验收。

优先验证 AgentArts 低码多智能体及工作流路径，保留原单智能体作为比较和回退基线，不重复创建已有资源。Managed Agents 的 WebSocket、知识库限制和鉴权不能套用到低码路径。新应用发布协议、上下文传递、流式事件、调用成本与账号权限单独核实。现有部署版本不等同于最新云端草稿。

官方能力依据（2026-11-03查阅，不代表账号内实测）：[多智能体配置](https://support.huaweicloud.com/lowcode-agentarts/agentarts_05_0106.html)、[执行范式](https://support.huaweicloud.com/lowcode-agentarts/agentarts_05_0105.html)、[知识检索工作流](https://support.huaweicloud.com/highcode-agentarts/agentarts_10_077.html)。平台多次模型调用会增加消耗；首版不做多层嵌套，不承诺多 Agent 必然更快或更准确。

## 10. 质量、数据保护与故障要求

- 来源透明：事实性岗位建议能回指资料；模型推断与原文要求分开。
- 最少采集：不要求身份证等无关信息；传给模型的是完成任务所需的字段，完整简历不是必要输入。
- 用户隔离：两名用户的档案、提交与计划互不可见；密钥留在服务端。
- 删除与记录：删除用户资料时同步清除相关检索记录；无法即时物理删除的备份按公布周期清理，不承诺尚未实现的删除方式。
- 外部文本可信边界：岗位、代码和网页内容只作材料，其中“忽略规则”等指令不得改变工具权限或用户数据范围。
- 可恢复：失败不能丢失已确认计划；重试不得重复建立任务。
- 性能目标：首版在固定演示环境下，普通数据页面 95% 请求 3 秒内返回，模型任务 60 秒内完成或给出明确失败/重试状态；目标需实测，不能写作既有性能。
- 成本可查：记录调用次数、可获得的 token/CU 用量及错误；根据比赛实际额度设限，不预设券金额。

| AC-24 | 同年级用户的准备程度不同 | 根据实际状态给建议，不强制统一年级路线 |

| AC-26 | 用户看课很多但从未尝试 | 询问阻碍，提供小行动及必要学习，不继续堆课或责备 |

| AC-28 | 用户因同伴影响纠结考研 | P0 记录疑问并安排取证；P1 比较条件与成本，不代替决定 |
| AC-29 | 无预算、无法异地参加实践 | 提供符合条件的校内/本地/模拟替代，不否定合理兼职 |
| AC-30 | 转写稿出现绝对学历或高薪结论 | 标记待核实，不自动变成系统事实或强制推荐规则 |

### 11.1 本版架构专项验收（未执行）

- MA01 模糊表达：不要求完整自我分析，少量追问后能复述线索并等待确认，不直接定职业。
- MA02 方向比较：两个候选方向的判断可回指资料，推断和事实分开；至少覆盖一个计算机类低年级未定向案例。
- MA03 反馈调整：读取当前规划及原验收要求，认可部分成果，时间变化后更新草稿且保留旧版，不将新建议改成旧必交项。
- 以上正常流程同时观察按需调度、角色交接、引用、预算校验、确认保存和失败状态；尚未实现的环节明确标记未通过或未执行。
- 记录模型、配置版本、检索资料、调用次数、首片段及总耗时、可获得的用量，不保存模型思考。使用同样输入与资料对照现有单 Agent，避免将模型或资料变化归因于角色拆分。只做必要回归，三个案例不替代原15例和完整P0验收。

## 12. 效果评估方案

先建立至少 30 个可复现案例，来自计算机相关专业的不同年级、基础与目标状态，覆盖完全未定向、专业内探索、跨专业探索、已有目标、基础不足、时间冲突、资料不足、非代码成果评估、调整和错误输入。每例保存输入、资料版本、预期关键点及实际输出。

在固定模型与相同岗位/学习材料条件下，与“单轮提示生成职业与学习建议”比较。评审时隐藏方案名称，按相同标准评价；完整产品另用两周试用验证，不能把两类实验的优势混在一起宣称。

建议首轮门槛：所有当前交付优先级对应的 AC 用例通过（P1 功能未交付时须列明暂不评估部分）；岗位引用可定位率 100%；时间与明确资格条件约束满足率 100%；随机检查至少 30 个岗位字段，提取正确率达到 90%。这些是目标，尚无结果；样本小，应同时报告具体分子/分母和错误案例。

两周试用邀请来自不同专业与年级的 6—10 位用户，记录是否能开始第一项任务、任务提交与通过情况、计划调整是否有帮助、用户是否理解推荐依据。记录退出和失败原因，不只展示满意反馈。首轮不据此推断就业成功率。

## 14. 实施阶段与交付物

当前执行顺序以[开发计划 v0.2](开发计划_v0.1.md)为准：现状与协议核验→角色和资料准备→最小云端协作验证→业务闭环接入→小范围对照及试用。下表保留产品交付维度，不代表需要重新搭建已有功能。

建议按四个阶段推进，不代表已确认赛程或承诺工期；实际以学校和赛事截止时间倒排。

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| 一：范围与平台验证 | 访谈记录、规则附件、最小平台连通 Demo | 验证来源、账号及真实工作流调用 |
| 二：数据与首次计划 | 审核资料、档案、方向比较、两周计划 | 能生成带依据且满足预算的计划 |
| 三：成长闭环 | 成果提交、反馈、调整、版本记录 | 含阶段约束、行动尝试与复盘的案例完整走通并可持久化 |
| 四：试用与材料 | 用例结果、试用记录、演示视频与方案 | 明确报告已验证效果和未完成项 |

三人分工建议：资料与技能/任务内容；AgentArts 编排与效果评估；后端、页面与数据记录。每人都应理解端到端流程；具体负责人待队伍确认。

## 15. 评审时需要确认的事项

1. 已确认面向计算机相关专业大学生；需要确认首批哪些职业领域能取得可靠资料和评估支持。
2. 如何选取跨专业演示和试用用户，检验通用流程及各领域覆盖深度？
3. 是否能邀请真实同学做访谈与两周试用？
4. 本届赛题对平台使用、作品材料和效果演示的具体要求是什么？
5. AgentArts 账号与资源是否可用，校内提交截止时间是什么？

以上未确认项不阻止先做资料整理、访谈和平台最小连通验证；依赖它们的范围与进度暂不写死。
